## החלטות מודעות – במה הקוד שונה מהפרומפט, ולמה

הפרומפט תיאר סכמה "אידיאלית" בלי להכיר את הקיימת. הסכמה הקיימת כבר רצה בפרודקשן ועברה 73 בדיקות
אבטחה, ולכן **לא שיניתי שמות של טבלאות ועמודות** – זה היה מחייב מחיקה ובנייה מחדש של מסד חי בלי שום
רווח תפקודי. ההבדלים:

| בפרומפט | בפרויקט | הסבר |
|---|---|---|
| טבלת `profiles` | `users` | אותו תפקיד (שורה לכל משתמש, FK ל-`auth.users`). |
| `items.title`, `items.condition`, `items.status` | `name`, `condition_rating`, `approval_status` | שינוי שם בלבד. |
| `role`: `user` / `admin` | `regular` / `admin` | שינוי שם בלבד. |
| `borrow_requests.borrower_id`, `quantity` | `requester_id`, `requested_quantity` | שינוי שם בלבד. |
| `loans` עם `item_id`, `borrower_id`, `start_date`, `due_date`, `quantity` | `loans` מצביעה על הבקשה בלבד | הנתונים האלה כבר שמורים בבקשה. שכפול שלהם היה יוצר שני מקורות אמת שיכולים לסתור זה את זה. |
| סטטוסי השאלה `return_marked` / `returned` / `overdue` | `returned_pending_confirmation` / `completed` / `late` | שינוי שם בלבד. |
| `loans.returned_at` | `actual_return_date` | שינוי שם בלבד. |
| `profiles.phone` | לא נוסף | צמצום מידע אישי: שני הצדדים של השאלה מקבלים זה את כתובת המייל של זה, וזה מספיק לתיאום. |
| מדיניות RLS לעריכה ומחיקה | אין מדיניות כתיבה כלל | מחמיר יותר: לקוחות יכולים רק לקרוא, וכל כתיבה עוברת דרך פונקציית מסד שבודקת מי הקורא. ראו `docs/RLS.md`. |
| הודעות toast | הודעה בתוך הטופס, ליד הכפתור | אותו מידע, נגיש יותר לקוראי מסך, ובלי ספרייה נוספת. |
| שלב 4 (AI) | לא בוצע | לפי ההוראה – רק אחרי אישור מפורש. |

מה שכן נוסף לסכמה: ב-migration `005` – `categories.icon`, `item_images.sort_order`, טבלת `email_log`;
ב-migration `006` – הטבלאות `conversations`, `messages`, `notifications`, `reports`.
